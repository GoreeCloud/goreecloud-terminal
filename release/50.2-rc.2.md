# GoreeCloud Terminal 50.2-rc.2

Release Lifecycle: **Release Candidate**

GoreeCloud Terminal 50.2-rc.2 is a separately versioned follow-up Release Candidate to the immutable published 50.2-rc.1 release. It carries the supported-workstation-validated Wardveil AT-SPI accessibility correction and post-RC1 stabilization/acceptance tooling while preserving the separation among source integration, release publication, deployment, production approval, and Stable promotion.

`50.2-rc.1 remains immutable`: its tag, public prerelease, approved release source, published bundle, checksum, and OSTree identity are historical release evidence and are not rewritten by RC2.

## Primary RC2 changes

- Carries the revised Wardveil semantic-label implementation that passed live supported-workstation exact AT-SPI accessible-name verification for `Remote terminal session`, `Containerized terminal session`, and `Elevated superuser terminal session` under the corresponding real detector-driven states before source integration.
- Preserves Local/unknown behavior without a misleading Wardveil context indicator and retains visible icon-plus-text context presentation.
- Adds a fail-closed production-identity no-host-filesystem candidate generator. The generated candidate may differ from the canonical production manifest only by removal of `--filesystem=host`.
- Adds a real repository-backed Flatpak transition acceptance workflow using the immutable published 50.2-rc.1 package as the rollback baseline. The workflow requires a cryptographically distinct candidate, verifies the narrower candidate has no host-filesystem permission, rolls back to the exact published RC1 OSTree commit, and verifies a synthetic application-data marker survives update, rollback, and ordinary removal.
- Expands the machine-readable source-acceptance contract to include Wardveil accessibility, supported-workstation contract, Flatpak permission-contract, and production no-host-filesystem transition gates.
- Refreshes Release Candidate lifecycle documentation and the read-only local API to identify the active candidate as `50.2-rc.2`.

## Packaging and permission boundary

Production RC application ID: `com.goreecloud.Terminal`

Development application ID: `com.goreecloud.Terminal.Devel`

Canonical launcher: `goreecloud-terminal`

Runtime/SDK: GNOME 50

The canonical production manifest remains `com.goreecloud.Terminal.json`. The canonical production and development permission sets remain aligned at this RC2 source-preparation boundary.

The no-host-filesystem package is an isolated acceptance candidate only. Automated build/update/rollback evidence does not authorize removal of `--filesystem=host` from the canonical production manifest. Affected supported-workstation PTY, local shell, working-directory, external-storage, host-agent, container, graphics/display, selection/clipboard, OpenSSH, coexistence, and recovery behavior must pass before that narrower permission set can be adopted.

## Accessibility boundary

The accessibility correction was accepted at the corrective-source/candidate boundary before merge. RC2 must independently preserve that behavior on the exact RC2 package. Publication acceptance therefore requires repeat verification of the exact accessible names under real Remote, Container, and Elevated states and confirmation that Local/unknown remains free of a misleading Wardveil indicator.

## Upgrade and rollback

The source now contains real repository-backed transition tooling in addition to the existing exact local-bundle lifecycle harness.

The repository-backed transition path has proven that an immutable RC1 baseline can update to a distinct generated production candidate and roll back to the exact published RC1 OSTree commit while preserving a synthetic application-data marker. That CI evidence is not represented as complete selected-release cross-version acceptance: the exact RC2 package and real post-rollback settings/profile/non-secret application-data compatibility remain separate governed gates.

Installing GoreeCloud Terminal still does not automatically migrate upstream Ptyxis settings. Optional migration remains dry-run by default, fail-closed against a non-empty target, privately snapshotted, and explicitly reversible.

## Security and privacy

RC2 introduces no telemetry, analytics, cloud synchronization, terminal-content collection, command collection, credential collection, or remote logging.

OpenSSH remains authoritative for SSH configuration, host-key verification, authentication, private keys, agents, forwarding, proxies, and connection policy. `sudo` and the operating system remain authoritative for privilege authorization. Wardveil context remains informational and does not authorize commands or sessions.

Release and acceptance evidence must exclude terminal contents, command history, clipboard contents, workstation identity, private host inventories, SSH configuration, private paths, accessibility-bus details, credentials, private keys, passwords, tokens, and other reusable secrets.
